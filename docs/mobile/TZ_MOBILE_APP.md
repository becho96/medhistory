# ТЗ: Мобильное приложение MedHistory

Версия 1.0 · 2026-07-09 · черновик для обсуждения

## 1. Цель и общие сведения

Нативное мобильное приложение (iOS + Android) для сервиса medhistory.ru, покрывающее весь основной пользовательский функционал веб-версии.

**Ключевое отличие от веба — офлайн-режим.** Целевой сценарий: пользователь на приёме у врача без связи (подвал поликлиники, роуминг, перегруженная сеть) открывает приложение и получает доступ ко всей своей медицинской истории — документам, динамике анализов, событиям здоровья — без интернета.

**Аудитория:** существующие пользователи веб-версии + новая аудитория кампании (мамы детей 0–7 лет), для которой мобильный телефон — основное устройство.

**Не входит в объём:** админ-панель (`/admin/*`), публичные лендинги (`/`, `/deti`), страница MCP OAuth consent — остаются веб-only.

## 2. Технологический стек (рекомендация)

**React Native + Expo (managed workflow, EAS Build).**

Обоснование:
- Один код на iOS и Android; соло-разработчик.
- Переиспользование экосистемы веб-версии: TypeScript, TanStack Query, Zustand, типы API-моделей и логика из `frontend/src/services/` переносятся почти без изменений.
- Expo закрывает сборку, подпись и OTA-обновления (EAS Update) без владения Xcode/Gradle-инфраструктурой.

Ключевые библиотеки:

| Задача | Библиотека |
|---|---|
| Локальная БД | `expo-sqlite` (SQLCipher-сборка) + Drizzle ORM |
| Кэш/синк серверного состояния | TanStack Query + persist-адаптер поверх SQLite |
| Локальное состояние | Zustand |
| Секреты (токены, ключ БД) | `expo-secure-store` (Keychain / Android Keystore) |
| Биометрия | `expo-local-authentication` |
| Камера/сканер документов | `react-native-vision-camera` + документ-сканер (обрезка, перспектива) |
| Push | FCM + APNs через `expo-notifications` (RuStore — см. §11) |
| Фоновая синхронизация | `expo-background-task` / BGTaskScheduler / WorkManager |
| Графики (динамика анализов) | `victory-native` |
| Крэш-репортинг | Sentry |
| Продуктовая аналитика | AppMetrica |

Альтернативы (Flutter, нативная разработка ×2) отклонены: нет переиспользования TS-кода и удвоение стоимости поддержки.

## 4. Функциональные требования по модулям

### 4.1 Аутентификация и локальный доступ
- Регистрация: email + пароль + два обязательных согласия 152-ФЗ (`terms_and_privacy`, `special_category`) — тексты и sha256 как в вебе, фиксируются через существующий `POST /auth/register`.
- Вход: `POST /auth/login` → пара access + refresh (см. §7.1).
- После первого входа — обязательная настройка PIN-кода (4–6 цифр) и предложение включить биометрию (Face ID / Touch ID / отпечаток).
- **Офлайн-вход:** PIN/биометрия открывают локальные данные без сети и без валидного access-токена. Сетевые операции возобновляются после фонового refresh при появлении сети.
- 5 неверных PIN подряд → стирание локальных данных (документы и БД), выход из аккаунта. Данные на сервере не затрагиваются.
- Выход из аккаунта = гарантированное стирание локальной БД, файлового кэша и ключей.

### 4.2 Документы
- Список с фильтрами и поиском как в вебе (`GET /documents`, `POST /documents/search`); офлайн — поиск по локальной БД (название, тип, специальности, summary).
- Загрузка: файл (PDF/фото из галереи) и **съёмка камерой** — мультистраничная, с автообрезкой и коррекцией перспективы, склейка страниц в один документ.
- Загрузка работает офлайн: документ попадает в локальную очередь (outbox) со статусом «Ожидает сети», отправляется автоматически при появлении соединения. Статусы: ожидает сети → загружается → анализируется → готов / ошибка (с ручным повтором).
- Просмотр: карточка документа — метаданные, summary, извлечённые лабораторные показатели, статусы назначений (`PATCH /documents/{id}/orders/{index}/status` — офлайн через outbox), просмотр оригинала.
- **Кэш оригиналов:** автоматически — последние 20 открытых; вручную — «закрепить офлайн» на любом документе; настраиваемый лимит кэша (по умолчанию 500 МБ) с вытеснением LRU (закреплённые не вытесняются). Индикатор «доступен офлайн» на карточке.
- Удаление документа — через outbox с немедленным скрытием в UI.

### 4.3 Лаборатория (динамика показателей)
- Список показателей с последними значениями и флагами отклонений (`GET /documents/labs/analytes`).
- График динамики показателя с референсными зонами (`GET /documents/labs/timeseries`), периоды: 6м / 1г / всё.
- Полностью работает офлайн: значения показателей хранятся в локальной БД, графики строятся локально.

### 4.4 События здоровья
- CRUD как в вебе (`/health-events`), справочник параметров кэшируется.
- Создание/правка/удаление офлайн — через outbox.

### 4.5 Интерпретации
- Список и просмотр сохранённых — офлайн.
- Создание новой (LLM) — только онлайн; кнопка при отсутствии сети заменяется на пояснение (паттерн как с pay-walled UI: не дизейблим молча, а объясняем и предлагаем действие).

### 4.6 Отчёты
- Генерация и список — онлайн; скачанный PDF сохраняется в файловый кэш и открывается офлайн; кнопка «Поделиться» (системный share sheet) — например, отправить врачу.

### 4.7 AI-ассистент
- Чат поверх существующего `WS /api/v1/assistant/ws?token=`, стриминг ответов, история сессий.
- Офлайн: история читается из кэша, поле ввода заменено плашкой «Ассистенту нужен интернет».

### 4.8 Семья
- Список профилей, переключатель активного профиля (глобальный, в шапке), CRUD членов семьи, приглашения — по существующему `/family/*`.
- Локальная БД хранит данные **всех** доступных профилей → переключение и просмотр работают офлайн. Приглашения/принятие — только онлайн.

### 4.9 Профиль, подписка, обратная связь
- Профиль: просмотр/правка (`GET/PATCH /auth/me`), просмотр выданных согласий.
- Подписка: текущий тариф и квоты (`GET /subscription/me`), активация промокода (`POST /subscription/activate`) — онлайн. Про покупки — §11.
- Feedback — форма, офлайн через outbox.

## 5. Офлайн-режим: архитектура

Принцип — **local-first для чтения**: UI всегда читает из локальной SQLite; сеть только наполняет и обновляет её. Нет разделения «онлайн-экран / офлайн-экран» — есть один экран и индикатор свежести данных.

### 5.1 Локальное хранилище
- SQLite + SQLCipher; ключ шифрования генерируется на устройстве и хранится в Keychain/Keystore.
- Таблицы зеркалируют серверные сущности: documents (+metadata из Mongo: summary, lab_results, classification), lab_values, health_events, interpretations, reports, family_profiles, chat_sessions/messages, user, subscription, справочники (параметры событий, типы родства).
- Файлы (оригиналы документов, PDF отчётов) — в приватной директории приложения с шифрованием; на iOS также `NSFileProtectionComplete`.
- Служебные таблицы: `sync_state` (курсор по каждой коллекции на профиль), `outbox` (очередь исходящих операций), `file_cache` (LRU-реестр).

### 5.2 Синхронизация: pull
- Дельта-протокол: `GET /api/v1/sync/changes?profile_id=&since=<cursor>` → изменённые/удалённые записи всех коллекций + новый курсор (см. §7.2). Удаления приходят tombstone-ами.
- Триггеры синка: холодный старт, возврат в foreground (не чаще раза в 5 минут), восстановление сети, pull-to-refresh, фоновая задача (~4 раза в сутки — чтобы к приёму у врача данные были свежими даже если приложение давно не открывали).
- Первичная синхронизация после входа: полная выгрузка структурированных данных всех профилей + оригиналы последних 20 документов; прогресс-бар, работа в фоне.

### 5.3 Синхронизация: push (outbox)
- Каждая офлайн-запись — операция в outbox: `{client_op_id (UUID), тип, payload, файлы, created_at}`.
- Отправка по порядку при появлении сети; `client_op_id` передаётся серверу для идемпотентности (повтор при обрыве не создаёт дубликат).
- Ошибки: сетевые — ретрай с экспоненциальной задержкой; 4xx (квота исчерпана, валидация) — операция помечается ошибочной, пользователь видит её в списке «Не отправлено» с действиями «повторить/удалить».

### 5.4 Конфликты
Модель данных конфликтам почти не подвержена (один пользователь, документы append-only, производные данные генерирует сервер). Правила:
- health_events, профиль: last-write-wins по `updated_at`; при проигрыше локальной версии — ненавязчивое уведомление.
- Правка сущности, удалённой на сервере: операция отбрасывается, пользователю показывается уведомление.
- Никаких экранов ручного merge в v1.

### 5.5 UX офлайна
- Постоянный индикатор в шапке при отсутствии сети: «Офлайн · данные на 14:32».
- Действия, требующие сети, не прячутся и не дизейблятся молча — показывают состояние и что произойдёт («отправится при появлении сети» / «нужен интернет»).
- Счётчик неотправленных операций с экраном очереди.

## 6. Мобильные фичи сверх веба

1. **Камера-сканер документов** (§4.2) — главный сценарий пополнения истории с телефона.
2. **Share extension**: «Поделиться в MedHistory» из другого приложения (PDF из почты, фото из мессенджера) → экран загрузки документа.
3. **Push-уведомления**: документ проанализирован; приглашение в семью; ошибка отправки из очереди. Опционально позже — напоминания о событиях.
4. **Биометрия/PIN** (§4.1).
5. **Deep links** `medhistory://document/{id}` — для переходов из push.

## 7. Доработки backend (обязательные, до старта мобильной разработки)

### 7.1 Refresh-токены
Сейчас access-токен живёт 24 часа, refresh-механизма нет — для мобильного это неприемлемо (постоянные разлогины). Требуется:
- `POST /auth/login` дополнительно возвращает refresh-токен (срок ~90 дней, ротация при каждом использовании, хранение в БД с возможностью отзыва).
- `POST /auth/refresh`, `POST /auth/logout` (отзыв).
- Access-токен сократить до ~30 минут для мобильных клиентов; веб не ломать (совместимость по флагу клиента или отдельному scope).
- Таблица устройств/сессий (device_id, платформа, last_seen) — базис и для push-токенов.

### 7.2 Дельта-синхронизация
- Эндпоинт `GET /sync/changes` (см. §5.2). Реализация: `updated_at` + монотонный курсор на каждую коллекцию.
- Tombstones: мягкое удаление (`deleted_at`) либо журнал удалений для documents, health_events, interpretations — иначе клиент не узнаёт об удалениях.
- Mongo-метаданные документа отдаются в том же ответе, что и Postgres-запись (одна точка синка для клиента).

### 7.3 Идемпотентность записи
- `POST /documents/upload`, `POST /health-events`, `POST /interpretations`, `POST /feedback` принимают заголовок `Idempotency-Key` (= `client_op_id`); повтор с тем же ключом возвращает исходный результат.

### 7.4 Push-инфраструктура
- Регистрация device-токенов (`POST /devices`), отправка через FCM/APNs, событие «анализ документа завершён» из пайплайна обработки.

### 7.5 Миграции
- Продолжаем нумерованный SQL-паттерн (`backend/migrations/0NN_*.sql`, следующая — 028): refresh_tokens/devices, deleted_at, индексы по `updated_at`.

## 8. Безопасность и 152-ФЗ

- Медицинские данные = специальная категория ПДн. Локальное хранение на устройстве пользователя допустимо (данные субъекта у самого субъекта), но обязательно шифрование всего кэша (§5.1) и защита доступа (PIN/биометрия).
- Токены и ключи — только Keychain/Keystore, никогда в AsyncStorage.
- Скрытие содержимого в переключателе приложений (blur/заглушка); на Android — `FLAG_SECURE` опционально в настройках (по умолчанию выключен, чтобы не мешать шарить скриншоты врачу).
- TLS-only, certificate pinning на `medhistory.ru` (с механизмом обновления пинов через OTA, чтобы не окирпичить приложение при смене сертификата).
- Не логируем PII (содержимое документов, значения анализов) ни в Sentry, ни в аналитику — только ID; правило то же, что на бэкенде.
- В сторах потребуется privacy-декларация (Apple Privacy Nutrition Labels, Google Data Safety) — категория Health.
- Согласия 152-ФЗ в регистрации идентичны вебу; тексты юр. документов встроены в приложение и обновляются вместе с релизом.

## 9. Нефункциональные требования

- Платформы: iOS 16+, Android 10+ (API 29+).
- Холодный старт до интерактивного состояния: ≤ 2 с на среднем устройстве; открытие закэшированного документа: ≤ 1 с.
- Полная работоспособность чтения при отсутствии сети — без крэшей, спиннеров-навсегда и пустых экранов.
- Язык: только русский (как веб).
- Размер приложения: ≤ 60 МБ при установке.
- Крэш-фри сессий ≥ 99,5 % (Sentry).
- Доступность: динамический размер шрифта, VoiceOver/TalkBack на ключевых экранах.

## 10. Этапы

**Этап 0 — backend-подготовка** (без него мобильная разработка блокируется): §7.1–7.3, каркас §7.4.

**Этап 1 — MVP.** Auth + PIN/биометрия; локальная БД и pull-синк; главный экран; документы (список, поиск, просмотр, кэш оригиналов, загрузка файлом/фото через outbox); лаборатория с графиками; события здоровья (полный офлайн-CRUD); переключение семейных профилей (чтение). Выход в TestFlight / внутренний трек Google Play.

**Этап 2 — паритет с вебом.** AI-ассистент; интерпретации; отчёты; управление семьёй (приглашения); профиль/подписка/промокоды; feedback; push «документ готов»; юр. документы.

**Этап 3 — мобильный полиш.** Камера-сканер с коррекцией перспективы; share extension; deep links; остальные push; публикация в App Store, Google Play, RuStore.

## 11. Открытые вопросы (решить до этапа 2)

1. **Платежи.** Apple/Google требуют in-app purchase для цифровых подписок, а IAP в РФ для российских карт не работает. Рабочий вариант v1: в приложении только промокоды и просмотр тарифа, покупка — на сайте (без прямой ссылки «купить» внутри iOS-приложения, иначе reject). Решить: оставляем так или делаем reader-модель.
2. **RuStore и push.** FCM на устройствах без Google-сервисов (часть Android в РФ) не работает. Оценить RuStore Push SDK как второй транспорт.
3. **Telegram-привязка из приложения** — flow привязки бота на мобильном (deep link в Telegram и обратно).
4. **MCP-интеграции** — остаются веб-only или нужны в приложении.

## 12. Критерии приёмки офлайн-режима (сквозной сценарий «приём у врача»)

1. Пользователь входил в приложение ≥ 1 раза, синхронизация завершалась. Телефон в авиарежиме ≥ 24 часов (access-токен истёк).
2. Приложение открывается по PIN/биометрии без сети.
3. Доступны: список и карточки документов, summary и лаб. показатели всех документов, оригиналы закэшированных, графики динамики всех показателей, события здоровья, сохранённые интерпретации, скачанные отчёты, данные всех семейных профилей.
4. Пользователь фотографирует новую выписку и создаёт событие здоровья — обе операции видны в UI сразу, лежат в очереди.
5. При появлении сети: очередь отправляется сама без открытия приложения (или при первом открытии), дубликатов не создаётся, документ уходит в анализ, приходит push о готовности.
6. Ни один экран в офлайне не показывает бесконечную загрузку или необработанную ошибку сети.
